### RAG基础知识

#### 召回率

```
召回率 = (检索到的相关文档数量) / (系统中所有相关文档的总数)
```

##### **Recall@K（最常用）**：只关心**前K个检索结果**中召回了多少。

```
Recall@K = (Top-K结果中相关文档数) / (总相关文档数)
```

**例如：**

- 总相关文档数：100篇
- Top-10结果中有8篇相关
- Recall@10 = 8 / 100 = **0.08（仅8%）**

**为什么用@K？**

- 用户只关心前几个结果（如搜索引擎的第一页）
- Recall@10 比全局召回更实用

#### 精确率

**找得准不准**（有没有找错？）

**例子：** 文档库有100篇相关文档

- 你的检索返回了50篇，其中40篇相关，10篇不相关
- **召回率 = 40/100 = 40%**（漏掉了60篇）
- **精确率 = 40/50 = 80%**（挺准）



#### 计算两个向量相似度方法

计算两个向量的相似度，本质上是用数学公式衡量两条“带箭头的线段”有多相似。在 RAG 中，主要有三个流派：

- **余弦相似度 (Cosine Similarity)**：看**方向**。只关心你们指的方向一不一样，不管长短。**这是 RAG 和大模型领域绝对的霸主，最常用。**
- **欧氏距离 (Euclidean Distance)**：看**绝对距离**。拿着尺子去量两个点之间的直线距离。
- **点积 / 内积 (Dot Product)**：看**方向 + 长度**。计算速度最快，常作为某些特定情况下的性能优化手段。

方向代表“语义”，长度代表“字数/强度”。方向远比距离重要的多。

#### 向量检索领域的三种核心索引算法

**Exact KNN 暴力检索  暴力穷举法 最准 但最慢**

​	- **技术原理：全表扫描。计算查询向量与数据库中每一个向量的距离，然后排序。**

**IVFFlat 倒排文件索引  物以类聚法 速度快 省内存 但准确率（召回率）降低**

 - **技术原理：利用k-Means等聚类方法，把所有向量划分成很多个簇（聚类中心）。查询时，先计算目标和哪个簇中心最近，然后只去那个簇里面做穷举对比。**

 - **当你拿着一个 Query 向量来搜索时，IVFFlat 默认的检索逻辑非常简单粗暴：**

   1. **用 Query 向量和内存里的 10000 个中心点计算距离。**
   2. **找到离得最近的 1 个中心点（代表找到了对应的收纳箱）。**
   3. **去硬盘里把这个箱子里的所有数据读出来，逐一计算距离，返回最相似的。**

   这样的话不准，因为只是用每个簇的中心点作为评判标准。那么我们可以在查询前动态执行 SET ivfflat.probes = 100;（增加探测的堆数量）。效果就是会找出来前100个距离最近的簇，然后依次计算簇中哪个向量距离查询向量最近，相当于扩大了搜索范围。

**HNSW 分层导航小世界 熟人社交网法 查询速度快 准确率高（接近Exact KNN）但吃内存**

- **技术原理：构建一个多层级的复杂图结构。最上层是稀疏的长途节点，越往下层节点越密。搜索时从顶层往下跳跃查找。**
- 参数：M（是每个节点可以建立的边数）、ef_search（是第0层，节点搜索的结果队列的长度）
- HNSW创建图的过程：HNSW通过多层图结构实现近似最近邻搜索。建图时，新节点随机决定最高层，然后从上向下逐层贪心定位到自己的层。**接着，从最高层开始，向下逐层（直到第0层），在每一层都找到最近的M个邻居，建立双向边连接，并对超出的邻居进行剪枝。** 搜索时，从顶层固定入口出发，每层贪心定位到1个最近节点作为下一层入口，到达第0层后，用优先队列做扩展搜索，直到候选集距离超过结果集最远距离为止。
- 第0层搜索的过程如下：**1、第0层搜索是从高层传来的最优节点出发，系统维护候选队列（小顶堆，按距离排序）和结果队列（大顶堆，大小固定为ef_search）。2、反复取出候选队列中最近的节点，扩展它的所有邻居，并不断更新两个队列。3、当候选队列的最近节点已经比结果队列的最远节点还远时提前终止，最后返回Top-K。**

**"在向量检索中，Exact KNN、IVFFlat、HNSW 是三种核心的近似最近邻搜索算法。它们对应了向量存储时的三种不同索引结构：暴力检索对应扁平存储（无索引），IVFFlat 对应聚类划分结构，HNSW 对应多层图结构。实际使用时，我们会根据数据量、内存限制和召回率要求，在向量数据库中选择一种作为索引类型。"**

#### RAG检索方式

### 基于关键词的精确匹配

##### BM25：基于关键词的精确匹配，通过计算关键词的词频（TF）和逆文档频率（IDF）来评估相关性。

​	"BM25是一种基于关键词的检索算法。给定一个查询，它会切分成词，对每个词计算在文档中的**词频**（经过饱和处理）、在整个文档集合中的**逆文档频率**（罕见词权重更高），并考虑**文档长度归一化**（短文档匹配更珍贵）。最终每篇文档得到一个总分，按分排序返回。

​	它的核心优势是速度快、可解释性强。缺点是只能精确匹配，不理解语义。在RAG系统中，通常与向量检索结合使用，形成混合检索。"

##### 全文搜索：依赖倒排索引技术，记录每个词出现在哪些文档中，能快速定位含有关键词的文档。

### 基于向量的语义匹配

为了解决“词不达意”的问题，这类方法将文本转换为高维空间的“向量”，通过计算向量间的距离来度量语义的相似度。

##### 密集检索：使用深度神经网络（如BERT）将文本映射为向量。

##### 稀疏检索：代表技术是**SPLADE**。它像BM25一样保留关键词的匹配能力，同时利用AI模型“扩展”出语义相关的词，既保证了关键词匹配的准确性，又融入了一定的语义理解能力。

##### 重排序（Reranker）：在初次检索后，使用更精密但计算成本更高的模型对结果进行二次排序，将最相关的信息排在最前面。

### 查询优化与增强策略

这类方法在用户正式发起检索之前，先对输入的问题进行加工，以提升检索效果。

**查询改写/扩展**：利用大语言模型（LLM）将用户模糊或简短的问题，改写成多个更清晰、更具体的查询语句，从不同角度去检索，以提高召回率。

### 目前生产效果最稳定的查询策略：混合检索

它旨在“取长补短”，结合了精确匹配和语义匹配的优势。

##### 混合检索：通常会结合BM25和密集向量检索，并通过Reranker模型对融合后的结果进行精排。

**相似度匹配 & 纯向量检索**：AI 靠“直觉”和“语义”去书海里捞出跟你问题意思最相近的内容（不看字面，看内在含义）。

**关系型过滤（元数据过滤）**：用死板的、精确的条件（比如作者、时间、租户ID）去卡死边界，就像 SQL 里的 `WHERE` 语句。

**混合检索**：把上面两者结合起来——**先用精确条件划定一个小圈子，再在这个小圈子里用 AI 去找最相近的内容**，这就是所谓的“预过滤（Pre-filtering）”。

想象你走进一个巨大的省图书馆：

- **纯向量检索**：你对图书管理员说：“我想找一本让人感觉很孤独、讲述人类在宇宙中渺小探索的小说。” 管理员不靠书名，凭着对书本内容的理解，给你拿来了《三体》、《沙丘》和《火星救援》。这就是**相似度匹配**（比对你的需求和书本内容的语义距离）。
- **关系型过滤**：你补充道：“我只要 2026 年之后出版的，而且必须是工业出版社的书。” 这个条件没有任何模糊地带，是就是，不是就不是。
- **后过滤（导致召回不足的错误做法）**：管理员先按“孤独、宇宙探索”找了 10 本最匹配的书（向量检索），拿过来之后再按你的条件一看（后过滤），发现里面只有 1 本是 2026 年后出的。你想借 5 本，结果只拿到了 1 本。**这就是题目中说的“召回数量不足”。**
- **预过滤（正确的做法）**：管理员先跑到“2026年以后、工业出版社”的书架前（关系型过滤），把不符合的书全排除掉，**然后只在这个小书架上**，根据“孤独、宇宙探索”的语义去找最匹配的 10 本书（向量检索）。这样就能保证找出来的书既符合硬性条件，意思又最接近。

**多路召回：**

1. **语义召回 (SemanticRetriever)**：靠向量相似度找，懂同义词。但可能漏掉精准的专有名词。
2. **关键词召回 (Bm25Retriever)**：经典的基于词频统计的算法，必须字面上匹配。
3. **查询改写 (QueryRewriteRetriever)**：用户说“那里面关于并发的...”，大模型先把它改写成“Java 并发编程核心知识”，再拿着改写后的话去搜。

**RRF 融合与重排 (Reranker)**： 上面三路找出来很多文档，怎么排序？RRF 是一种无需权重的数学算法，综合三路的排名。最后再用一个专门的 `LlmReranker`（它比普通的 Embedding 模型更慢、但更精确）对 Top 9 进行精确打分，选出最相关的 Top 3，拼接到 Prompt 里喂给大模型。

### 相关问题

#### 如何全面地评估一个RAG系统的性能？请分别从检索和生成两个阶段提出评估指标

全面评估一个 RAG（检索增强生成）系统，不能像测试传统软件那样只看“输出结果对不对”，而是要像考核两个独立部门的绩效一样，分别给**负责找资料的“档案局”（检索阶段）**和**负责写报告的“秘书处”（生成阶段）**打分。业界目前最主流的标准是考核三大指标：**上下文相关性、忠实度、回答相关性**。

**整体思路或主线**

如果一个 RAG 系统给出了糟糕的回答，你必须能“定责”。 假设用户提问：“PgVector 怎么建 HNSW 索引？” 整个 RAG 的主线是：

1. **提问 (Question)** -> 触发检索。
2. **检索阶段 (Retrieval)** -> 从 PgVector 知识库中搜出几个文本块（**Context**）。
3. **生成阶段 (Generation)** -> 大模型看着这些文本块，写出最终**回答 (Answer)**。

**所以，评估框架（如业界著名的 `Ragas` 或 `TruLens`）的核心逻辑，就是在这三个节点（Question, Context, Answer）之间两两比对，找出是谁掉了链子。**

**检索阶段：**question和context

1. 上下文相关性：搜出来的这些文本块，到底跟用户的问题沾不沾边？有没有搜出很多废话？
2. 召回率 / 命中率：系统有没有把能够回答问题的“关键知识点”全都找出来？是否存在遗漏？

生成阶段：

1. 忠实度 / 无幻觉：context和answer
   1. 大模型的最终回答，是不是**百分之百**来源于你提供给它的文本块？有没有夹带私货或胡说八道？
2. 回答相关性：answer和question
   1. 大模型给出的回答，有没有真正解答用户的原始提问？是不是答非所问？

#### 如何选择合适的Embedding模型？

1. 多语言和领域支持：适合英文的模型不一定适合中文。
2. 向量维度：维度越高，区分句子语义的能力更强，更精准，但是所占的内存空间更大。
3. 最大上下文长度：模型一次最多能把多长的文本转化为向量。如果我们给模型一段超过它能处理的长度的chunk，那么模型只会处理它能处理的长度，后半部分内容直接丢弃，也就不会存储到向量库中，导致信息丢失。
4. 部署方式和成本问题：本地部署还是云端部署。
