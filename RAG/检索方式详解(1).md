# 信息检索方式详解

## 一、检索方式全景

```
检索方式
├── 稀疏检索（词频统计）
│   ├── TF-IDF
│   └── BM25
├── 密集检索（向量语义）
│   ├── 暴力全扫描（Brute-force）
│   └── ANN 近似最近邻
│       ├── FAISS（IVF / HNSW / PQ）
│       ├── ScaNN
│       └── Milvus / Weaviate（向量数据库）
└── 混合检索
    └── 稀疏 + 密集（BM25 + Dense + RRF）
```

---

## 二、稀疏检索

### 2.1 TF-IDF

**原理**

每个词用两个维度衡量重要性：

```
TF(term, doc)  = 该词在文档中出现次数 / 文档总词数
IDF(term)      = log(总文档数 / 包含该词的文档数)
TF-IDF = TF × IDF
```

文档表示为稀疏向量（词表大小维度，大部分为0），检索时计算 query 和所有文档的余弦相似度。

**示例**

```
文档库：
  doc1: "The food was great"
  doc2: "The service was terrible"

query: "food great"
刚开始应该是建立了词表但是停用词概念，the与was自身idf是0，停用了
TF-IDF向量（简化）：
  query: [food:0.8, great:0.6, service:0, terrible:0]
  doc1:  [food:0.7, great:0.5, service:0, terrible:0]  → 相似度高
  doc2:  [food:0,   great:0,   service:0.7, terrible:0.6] → 相似度低
```

**适用场景**

- 文档数量少（<10万），对速度要求不高
- 关键词匹配为主的场景（法律文档、代码检索）
- 需要可解释性（能看出哪个词贡献了分数）

**缺点**

- 不理解语义，"food" 和 "meal" 是完全不同的词
- 词表维度极高（数万维），内存大
- 无法处理同义词、多义词

---

### 2.2 BM25（Best Match 25）

**原理**在tf计算进行修改

TF-IDF 的改进版，解决了两个问题：
1. TF 饱和问题（一个词出现100次不应该比出现10次好100倍）
2. 文档长度归一化（长文档天然词频高，需要惩罚）

```
BM25(q, d) = Σ IDF(t) × [tf(t,d) × (k₁+1)] / [tf(t,d) + k₁×(1 - b + b×|d|/avgdl)]

参数：
  k₁ ∈ [1.2, 2.0]：TF 饱和速度，越小饱和越快
  b  ∈ [0, 1]    ：长度惩罚强度，b=0不惩罚，b=1完全归一化
  avgdl          ：语料库平均文档长度
```

**与 TF-IDF 的区别（图示）**

```
TF 贡献值
  ↑
1.0|              ___________  ← TF-IDF（线性增长）
   |         ____/
   |    ____/
   |___/____________→ 词频
   0   1  2  3  4  5

  ↑
1.0|        ______  ← BM25（饱和，高频词收益递减）
   |     __/
   |  __/
   |_/____________→ 词频
   0  1  2  3  4
```

**适用场景**

- 搜索引擎的初级召回（Elasticsearch 默认就是 BM25）
- 对精确关键词匹配要求高的场景
- 作为混合检索的稀疏端

**相较于 TF-IDF 的优势**

| 问题 | TF-IDF | BM25 |
|------|--------|------|
| 高频词饱和 | 线性增长，无上限 | 饱和曲线，收益递减 |
| 长文档偏差 | 无归一化 | 参数 b 控制长度惩罚 |
| 实际效果 | 一般 | 显著更好，工业标准 |

**缺点**

- 依然是词袋模型，不理解语义
- "excellent cuisine" 和 "great food" 对 BM25 来说没有任何关联

## 三、密集检索（向量语义检索）

### 3.1 暴力全扫描（Brute-force Exact Search）

**原理**

把所有文档编码成稠密向量（如384维），检索时计算 query 向量与每个文档向量的相似度，取 top-k。

```python
# 你的项目实现
query_emb = model.encode("The food was great [SEP] food")  # (1, 384)
sims = cosine_similarity(query_emb, self.demo_embeddings)   # (1, N)
top_k = np.argsort(sims[0])[::-1][:k]
```

**复杂度**：O(N × d)，N=文档数，d=向量维度

**内存**：5000条 × 384维 × 4字节 ≈ 7.3 MB，极小

**适用场景**

- 文档库 < 10万条
- 对精度要求极高（精确检索，无近似误差）
- GPU 可用时（矩阵乘法高度并行，5000条只需 2ms）

**优势**

- 结果 100% 精确，无近似误差
- 实现简单，零额外依赖
- 小规模下速度不输 FAISS

**缺点**

- 线性复杂度，百万级时慢
- 不可扩展

---

### 3.2 FAISS（Facebook AI Similarity Search）

FAISS 是近似最近邻（ANN）检索库，用各种索引结构跳过大量不相关向量。

#### 3.2.1 IndexFlatIP / IndexFlatL2（精确索引）

```python
import faiss
index = faiss.IndexFlatIP(384)   # 内积（等价于归一化后的余弦）
index.add(demo_embeddings)        # 加入向量
D, I = index.search(query_emb, k=30)  # 返回距离D和索引I
```

和暴力全扫描完全等价，只是用 FAISS 的 C++ 实现加速矩阵运算。

适用：< 10万条，要精确结果。

---

#### 3.2.2 IndexIVFFlat（倒排列表索引）

**原理**

```
第一步：训练阶段
  对所有向量做 k-means 聚类，得到 nlist 个聚类中心（"桶"）

第二步：建索引
  每个向量分配到最近的聚类桶中

第三步：检索
  query → 找最近的 nprobe 个桶 → 只在这些桶内暴力搜索
```

**图示**

```
向量空间：
  [桶1: food类语义向量]  ← query落在这里，只搜这里
  [桶2: service类语义]
  [桶3: price类语义]
  [桶4: ...]
  ...（共nlist=100个桶）

nprobe=5 → 只进入最近的5个桶，跳过其他95个桶
```

**参数**

```python
quantizer = faiss.IndexFlatIP(384)
index = faiss.IndexIVFFlat(quantizer, 384, nlist=100)
index.train(demo_embeddings)       # 必须先训练聚类中心
index.add(demo_embeddings)
index.nprobe = 10                  # 搜索时进入几个桶，越大越准但越慢
D, I = index.search(query_emb, k=30)
```
```
**适用场景**：百万级文档库

**优势**：检索复杂度从 O(N) 降到 O(N/nlist × nprobe)

**缺点**：有近似误差（nprobe 太小可能漏掉最近邻）；需要训练阶段

---

#### 3.2.3 IndexHNSW（分层可导航小世界图）

**原理**

构建多层近邻图，底层是稠密图（每个节点连K个邻居），上层是稀疏图（长程跳跃）。检索时从顶层入口出发，贪心地向 query 方向移动，逐层下降。

```
Layer 2（稀疏，长程跳跃）:  1 ———— 5 ———— 9
                              ↓         ↓
Layer 1（中等密度）:     1—3—5—7—9—11
                         ↓ ↓ ↓ ↓ ↓  ↓
Layer 0（稠密，精确）:  所有节点互连
```

**参数**

```python
index = faiss.IndexHNSWFlat(384, M=32)  # M=每个节点连接数
# 建图：自动，无需训练
index.add(demo_embeddings)
# ef_search 越大越准，越慢
index.hnsw.efSearch = 64
D, I = index.search(query_emb, k=30)
```

**适用场景**：百万级，对延迟极度敏感的在线服务

**优势**

- 检索延迟最低（对数复杂度）
- 无需训练阶段
- 召回率高（近似误差小）

**缺点**

- 建图内存消耗大（每个节点存32个邻居指针）
- 不支持动态删除节点

---

#### 3.2.4 IndexPQ（乘积量化）

**原理**

把384维向量切成 M 段（如 M=8，每段48维），每段单独做 k-means 量化，用聚类中心编号代替原始值。

```
原始向量：[0.021, -0.013, ..., 0.087]  → 384个float32 = 1536字节
PQ压缩后：[3, 7, 2, 5, 1, 8, 4, 6]    → 8个uint8 = 8字节（压缩192倍）
```

**适用场景**：亿级文档，内存极度受限

**优势**：内存压缩比极高

**缺点**：精度损失最大，通常与 IVF 结合使用（IndexIVFPQ）

### 3.3 其他 ANN 实现

| 实现 | 特点 | 相较 FAISS 的优势 |
|------|------|-----------------|

## 四、混合检索

**原理**

同时用稀疏检索（BM25）和密集检索（Dense）各召回一批候选，用 RRF（Reciprocal Rank Fusion）合并排名：

```python
# RRF 公式
score(doc) = Σ 1 / (rank_i + k)    # k=60 是常数，防止排名第1的文档权重过大

# 示例
doc_A: BM25排名=1, Dense排名=5
  score = 1/(1+60) + 1/(5+60) = 0.0164 + 0.0154 = 0.0318

doc_B: BM25排名=10, Dense排名=2
  score = 1/(10+60) + 1/(2+60) = 0.0143 + 0.0161 = 0.0304
```

**架构图**

```
query
  ├── BM25 检索 → [doc3, doc7, doc1, doc9, ...]
  └── Dense 检索 → [doc1, doc3, doc5, doc2, ...]
                         ↓ RRF 融合
                   [doc1, doc3, doc7, doc5, ...]  → CrossEncoder 精排 → top-k
```

**适用场景**

- 工业级 RAG 系统（LangChain、LlamaIndex 默认推荐）
- 既要关键词精确又要语义泛化的场景
- 问答系统、企业知识库

**优势**

| 场景 | BM25 | Dense | 混合 |
|------|------|-------|------|
| 精确关键词（产品型号） | ✓ 好 | ✗ 差 | ✓ 好 |
| 语义相近（同义词） | ✗ 差 | ✓ 好 | ✓ 好 |
| 专有名词（人名地名） | ✓ 好 | ✗ 差 | ✓ 好 |
| 语义理解（情感分析） | ✗ 差 | ✓ 好 | ✓ 好 |

## 六、本项目的选择理由

**当前方案：暴力全扫描（sklearn cosine_similarity）**

```
demo 库规模：3000~5000条
向量维度：384
GPU 全扫描耗时：~2ms
supar 解析耗时：50~200ms（真正瓶颈）
内存占用：≈7.3MB
```

结论：**检索不是瓶颈，暴力扫描精度最高、实现最简，是当前规模的最优选择。**

**扩展路径**

```
当前（<1万条）  → 暴力全扫描
↓ 库扩展到100万条
→ FAISS IndexIVFFlat（nlist=1000, nprobe=50）
↓ 需要关键词+语义双保险
→ BM25 + Dense 混合检索 + RRF
↓ 需要持久化 + 多并发
→ Milvus / Qdrant 向量数据库
```
